# GYUTRON Operations — 独立实例商业交付手册

更新：2026-11-03。适用对象是部署运营人员与交付验收人员。本文件描述当前产品的交付模型与要求，实际已启用模块、版本、验收结果和生产状态以随包manifest、发布记录及 `HANDOFF.md` 为准。

## 1. 可交付的产品与边界

GYUTRON Operations采用**每客户独立Worker、D1数据库、私有R2存储与限流KV**。客户之间通过云资源和部署边界隔离，不使用一个共享数据库里的tenant_id。客户名称配置不等于租户隔离；复制实例时必须创建或明确选择属于该客户的独立资源。

当前版本提供客户、商机、跟进任务、活动记录、官网提交收件箱、可恢复归档、筛选导出、审计、团队权限与运维状态；工业报价已完成独立验收和生产发布。原有订单请求与事件运营页继续受新会话及角色保护。工作台及报价固定文案支持EN/中文/DE/日本語，用户录入的商业正文不自动翻译。

独立starter的入口约定是受保护的 `/admin` 工作台及必要静态资源；它不打包GYUTRON官网公共表单、只读Data API或Shop主机映射/下单路由。不要把品牌官网生产入口原样复制进客户实例。收件箱/原有运营表可保存数据，不表示独立包已经提供公共提交或电商接入；相应接入需另做验证。独立包验证器必须检查这些路由边界后才可交付。

这个交付模型适合“软件实例部署、配置、维护与服务”业务。当前没有共享库多租户、自助开通租户、自助订阅收费、支付结算、库存会计、财务总账、SSO或MFA，不能把这些列为已具备。系统也不自动发送报价邮件、拨号或收款；记录email/call活动是人工业务记录，不是外部通信成功证明。

## 2. 交付包必须包含与排除的内容

交付包应固定源commit，包含必要应用源码、锁定依赖、数据库迁移、管理端静态资产、配置模板、许可清单、安装/升级/恢复说明、可复现检查与验收记录。包内文件清单和SHA-256由生成工具产生；接收方验证后安装，不能把不同版本的Worker与迁移拼装。

不要把GYUTRON生产 `wrangler.toml` 的资源ID原样带给第二个客户。模板必须使用明显的占位配置，客户域名和Worker名称也应独立。不得携带 `.dev.vars`、`.env`、OAuth缓存、生产数据库导出、备份JSON、恢复SQL、私密R2对象、真实客户资料、调试账号或生产cookie。不要把整个工作目录直接压缩成商业安装包。

默认GYUTRON视觉资产、名称和外链属于品牌配置；允许客户改名并不自动授权其使用其他商标或让所有硬编码外链自动完成白标化。交付前检查logo、站点链接、发行方资料、支持联系方式、隐私文案及打印文档中的品牌信息。

## 4. 独立部署流程

1. 校验交付包manifest与SHA，记录源commit、应用版本、迁移上限和验收版本。使用新目录，不复用已有客户的私密状态目录。
2. 按包内README安装Node24及锁定依赖，使用 `npm ci`。不随意升级Wrangler或替换包管理器后仍声称是同一已验收版本。
3. 认证属于交付主体的Cloudflare账号，核实Worker、D1、R2、KV的实际账户与资源。新客户使用独立资源；已有客户升级保持其已核实绑定，不重新创建或替换健康资源。
4. 将资源的真实ID填入该客户配置。保留应用要求的binding名称 `DB`、`R2`、`RATE_LIMIT`，以及包内实际使用的资产binding。不要猜ID，也不要复制GYUTRON生产ID。
5. 配置品牌、时区与秘密；应用本地迁移并执行测试，再对目标客户数据库应用增量迁移。升级已有数据前先做原生SQL导出或记录恢复点，验证备份可读且私密。
6. 验证bundle、按该包部署入口发布；使用客户实际域名或Worker URL检查登录、API、静态资源、关键业务流程及cron配置。推送Git或CI成功不等于Worker已经上线。
7. 验收该客户实际启用的登录方式；如另行启用命名员工入口，则创建对应账号并验证角色权限与停用撤销。移除交付测试记录和临时账号，向客户交付访问方式、维护联系人和恢复责任。

迁移文件按顺序执行并保留真实 `d1_migrations`。现有实例不能通过编辑旧迁移或手工改表伪装升级。出现结构不符时先查明，不用IF NOT EXISTS掩盖错误结构。

## 5. 配置、身份与秘密

| 项目 | 当前作用与要求 |
|---|---|
| `ADMIN_WORKSPACE_NAME` | 工作区显示名称；长度受服务端限制 |
| `DATA_SOURCE_ID` / `DATA_SOURCE_NAME` | 该实例的数据来源标识；不同客户使用不同值 |
| `ADMIN_TIMEZONE` | 业务日期的IANA时区；默认Asia/Singapore；存储时间仍为UTC |
| `ADMIN_LOGIN_MODE` | 默认留空，仅显示所有者密码；独立客户明确选择后可设为`team`显示可选员工邮箱入口，沿用已有角色和会话验证 |
| `ADMIN_PASSWORD` | 部署所有者密码，Worker secret保存；由实例所有者决定。新商业实例可选密码管理器生成的长随机值；当前GYUTRON按用户指定值保留，不在仓库记录原文 |
| `ADMIN_SECRET` | 独立、足够随机的Worker secret；轮换会使已有owner会话fingerprint失效 |
| `IP_HASH_SALT` | 限流/隐私处理的独立随机盐；不要跨客户复用 |
| `DATA_API_KEY` | 独立starter不暴露公共Data API，因此不需要配置；未来显式增加该集成时才独立设置、验证并最小权限分发 |

秘密只通过受控的Worker secret流程设置，不写入Git、发行包、命令参数、截图或日志。示例配置只能含占位值。不要让部署人员为了方便给多个客户共用同一owner密码、R2桶或API key。

owner是部署秘密控制的恢复/管理身份，无法通过Team页面移除；因此owner操作的审计身份是“Workspace owner”，不等同于具名员工。当前GYUTRON默认界面按用户决定只保留共享密码登录，不展示账号字段。命名staff、manager/sales/viewer权限与Team接口仍保留；独立客户选择`ADMIN_LOGIN_MODE=team`后才显示员工邮箱入口，安装时必须验收该客户实际启用方式。没有员工自助密码重设或邮件邀请；启用命名员工后，初始密码通过受控渠道交付，重置撤销既有会话。

员工密码使用带随机salt的scrypt；opaque会话token只存hash，每次请求读取当前active/role。当前会话最长8小时、闲置2小时；退出、停用、密码或角色相关变更执行撤销。部署者不应把界面隐藏按钮当作权限控制的证据，必须执行负向API验收。

## 6. 数据连接与报价真实性

收件箱仅显示发送到该实例数据库的真实记录。独立部署本身不会自动接通客户官网、邮箱、Alibaba或其他CRM。每个数据接入需要明确来源、字段、权限、重复提交策略和实际端到端验收；未接通时显示真实空状态。

工业报价发布后，交付验收应确认：单一币种、正确minor unit、精确整数计算、固定手填折扣/税费/运费明确标注、issued内容不可变、修订产生新版本、重复签发不重复编号、打印来自冻结快照。报价是商业报价文件，不能宣称已付款、已发邮件、已开具税务发票或自动符合任何司法辖区的税务规则。

客户/商机金额是潜在商机金额，报价总额也不是已确认收入。没有真实付款/会计接入时，不提供虚构营收、应收账款或付款成功状态。

## 7. 私有备份、恢复与容量

每日cron备份、owner重新验证密码后的手动备份、R2回读校验和verified commit marker使用同一备份实现。新增持久表必须同步备份清单与恢复测试，不以成功备份旧表代表完整覆盖。

当前应用JSON快照上限为25,000行持久数据、8MiB完整JSON；SQL端预检查和事务内guard在超限时不返回大数据行，给出明确失败。schema/manifest预留256KiB，业务数据预算略低于8MiB。报价每条item也是一行，审计与事件也计入容量，不能把上限解释为25,000张报价。

长期或较大实例应安排D1原生导出/Time Travel或经过独立验收的分块备份。不能在到达上限后仍承诺应用cron快照正常；运维需跟踪实际行数、失败事件及最新对象时间。保留30个verified daily日期、12个weekly日期；无marker的旧备份/失败孤儿不占verified名额，也不会自动清理。

R2桶必须保持私密：关闭r2.dev公开访问，不绑定会公开整个桶的自定义域名，不把backups登记为下载资源。备份含客户资料和用户密码hash，访问权按敏感数据处理。恢复默认不恢复任何live session，所有账号重新登录；Worker secrets单独保管。

完整恢复步骤、格式兼容、隔离演练和现有实测范围见 `admin-backup-recovery.md`。每个客户交付前都应在隔离目标实际恢复并核对表计数、外键、登录、角色、读写、审计与会话为空；恢复时间和丢失窗口实测后再填写，不预先承诺RPO/RTO。

## 8. 运维责任与发布回退

交付记录应明确谁负责Cloudflare账号/域名费用、资源额度、依赖更新、员工离职停用、owner秘密轮换、备份检查、恢复执行和客户支持。应用可用、云服务可用及业务数据正确是不同检查，需各自记录。

当前已有Worker observability、业务audit/event、健康检查和System运维元数据；这不自动等于有人接收告警。对外提供托管服务前，配置实际告警接收者、故障升级方式和巡检频率，并完成故障演练。不要填写未经实测的可用率或SLA。

每次发布记录源commit、Worker版本、数据库迁移、备份ID、CI和生产验收。代码回退优先选择已知兼容的Worker版本；Worker回退不会倒退D1/R2数据。不要把旧snapshot直接覆盖到仍在接收新业务的生产库；数据库恢复先在新的隔离目标验证后按维护窗口执行。

## 9. 客户验收与移交记录

对每个独立实例至少完成：

- 实际资源归属、品牌/时区/域名、发行包hash和版本核对。
- owner共享入口、CSRF/限流/退出重放；若该客户另行启用命名员工，则同时验收viewer写入/导出拒绝、sales归档/审计拒绝、manager授权行为与停用撤销。
- 客户→商机→任务→活动闭环，官网提交/转换的真实来源与幂等性，归档/恢复和并发冲突。
- USD/JPY金额、混合币种分组、CSV公式防护、分页/过滤完整性。
- 报价模块若包含在交付中，按其完整金额、签发/修订/冻结与打印验收，不仅检查总额展示。
- 实际R2私密设置、手动备份、cron配置、隔离恢复、容量边界、告警接收者及升级/回退流程。
- 桌面/平板/手机、键盘、加载/空/错误/成功状态、长文本、最新确认框与System界面。
